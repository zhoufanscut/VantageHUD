# AGENTS.md

Self-contained Claude Code statusline (HUD). Reads one JSON payload on stdin, prints the status line on stdout. Pure Node built-ins, ESM, **zero dependencies**. See `README.md` for end-user setup/proxy/env docs — this file is the agent-specific map.

**Shared vocabulary lives in [`GLOSSARY.md`](GLOSSARY.md)** — read it if a term here is unfamiliar (element, fragment, palette/token, session key, render context, safeMode, …). It also flags the easy-to-confuse pairs (`statusline` vs `statusLine`, render context vs context window). When you add an element/theme, add its term there too.

## Source of truth & build (read first)

- **The `.js` files under `src/` ARE the source. Edit them directly.** They look like transpiled TypeScript (JSDoc `@param` types, `??`, a comment in `src/hud/types.js` referencing a non-existent `render.ts`), but there is **no `tsconfig`, no `.ts` files, no build step, no `node_modules`**. Do not look for or create a build pipeline; do not introduce `.ts`.
- **No package manager install is needed or wanted.** `package.json` has no deps, no scripts. Never add a dependency or `node_modules` — the project's entire value proposition is being self-contained Node built-ins only (`"type": "module"`, `engines.node >=14.17`).
  - The floor is **Node ≥ 14.17** (`engines`); nothing older is tested. The code no longer calls `crypto.randomUUID()` (temp names and lock nonces come from `uniqueToken()` in `src/lib/atomic-write.js`), but `node:` ESM specifiers (git.js, svn.js) still need ≥ 14.13.1. `statusline.mjs` checks the version at startup (below).
- Shared utilities live in **`src/lib/`** (recently moved from `src/utils/`, `src/cli/utils/`, `src/platform/`). Import helpers from `../lib/...`.

## Verification (there are no tests)

No test runner, no linter, no formatter, no typecheck, no CI. The only verification is the smoke test — **run it after any change**:

```sh
echo '{"session_id":"t","cwd":"'"$HOME"'/example","effort":{"level":"high"},"model":{"id":"claude-opus-4-8","display_name":"Opus 4.8"}}' \
  | HUD_SYNC_REFRESH=1 sh statusline.sh statusline.mjs
```

Expect one line containing `opus:high`. `HUD_SYNC_REFRESH=1` renders *this* payload synchronously and prints that line — without it the wrapper's hot path prints the **previous** frame from the cache and only refreshes in the background, so a code change would look like it had no effect (that was the behaviour until 2026-09, even with the flag); `HUD_DEBUG=1` adds stderr diagnostics. To exercise the renderer alone: `... | node statusline.mjs`. No `session:` fragment appears: the sample payload names no transcript, and the element hides rather than reading `0m`.

## Execution flow (not obvious from filenames)

```
Claude Code → statusline.sh → find-node.sh → statusline.mjs → src/hud/index.js → src/hud/render.js → src/hud/elements/*.js
```

- `statusline.sh` (POSIX, no bashisms) is a **caching wrapper**, not just a launcher. Hot path = `cat` the last rendered line for this session and kick a background Node refresh for the *next* frame. It costs ~12 processes (was ~32; counted with `/proc/sys/kernel/ns_last_pid` while the render lock was held, 21.8 → 12.9 ms a frame here) — every helper on it is a builtin or a single fork (`file_mtime` and the config stamp are one `stat`, the session id one `sed`, the sanitizing `tr` runs only for a key with an unsafe byte); keep it that way, forks are what Windows/Git Bash is short of. First render per session is **synchronous** because the next trigger can be a long way off: Claude Code runs the `statusLine` command once at session start (resume included) and then only when a new assistant message arrives, `/compact` finishes, the permission mode changes, vim mode toggles, a configured `refreshInterval` elapses, or a rate-limit window / warm prompt cache in the last payload reaches its `resets_at` / `expires_at` — so an async-only first frame would leave `[HUD] Starting...` on screen until the user sends something. Two more consequences of that contract: updates are debounced 300 ms and **an in-flight command is cancelled when a new trigger fires**, which is the other half of why the hot path must stay a `cat`; and with no `refreshInterval` set the triggers go quiet whenever the session is idle (a lead waiting on background teammates is the documented case), so every time-based fragment — `session:`, the limit countdowns — stands still until the session moves. Elements that track live state are therefore viable only with `refreshInterval` (minimum `1` second) configured. **Config edits are picked up on the next frame, not the one after:** the hot path is bypassed (forcing a synchronous re-render) whenever the config's `mtime:size:inode` stamp differs from the one recorded in `cache/<session>/config.stamp` when the cached line was rendered — see `config_changed` (the config path mirrors Node's `getHudConfigFile`: `HUD_CONFIG` override, used verbatim on both sides, else `<install>/config.json`). Inequality, not "newer than": an mtime comparison forced a synchronous render on *every* frame for a config dated in the future, and missed an edit in the same second as the render. The stamp is taken *before* Node starts, so an edit landing mid-render is not recorded as shown. The one miss left is a second in-place edit of the same size within the same second. **Time triggers are honored the same way:** Node writes `cache/<session>/statusline.deadline`, an empty file whose *mtime* is the earliest future `rate_limits.*.resets_at` / warm `prompt_cache.expires_at` in the payload, less a second (`getNextTimedTrigger`, `atomicTouchSync`); once `stdin.json` — written by the current frame, so its mtime is "now" — is newer (`-ot`, a builtin in dash/bash/busybox/macOS sh; not POSIX, and a shell without it just keeps the one-frame lag), that frame renders synchronously. Without it the frame Claude Code fires at a reset showed the line from before the reset, and an idle session has no next trigger to correct it. The sync path deletes the passed deadline before rendering, so a failing render cannot make every later frame synchronous. When that sync render can't run (lock held / render failed), the wrapper still prefers the stale cached line over the `[HUD] Starting...` placeholder. Two failure shapes, handled differently on purpose: a render that prints **nothing** (crash, timeout, no `node`) keeps the last good line, while one that prints a `[HUD] …` fallback line (a caught runtime error) **replaces** it, because that line points at stderr — kept as `statusline.err` until the next good render. **A wrapper killed mid-render must not cost the cached line**, or every later frame takes the slow synchronous path and can be killed the same way — a loop seen on a loaded Windows box (25+ orphaned `statusline.<PID>.tmp`, each a complete line, a leftover `render.lock`, no `statusline.txt`), and reproduced here by killing the wrapper's process group after the render: the old code left exactly that. So the wrapper passes `HUD_OUTPUT_FILE` and Node writes the good line there itself (atomically) the moment it has one; the wrapper's own `mv` stays as the path for older renderers and for the `[HUD] …` fallback. The synchronous render also passes `HUD_SYNC_RENDER=1`, which makes `svn status` serve its memo instead of walking (below), and `HUD_USAGE_BUDGET_MS` (from `HUD_SYNC_USAGE_BUDGET_MS`, default 1000): past it `getUsage` serves the cached numbers **without writing a failure** (a `network` entry would suppress fetches for 2 min), and Node exits once its line is flushed — the abandoned request otherwise held the process for the proxy CONNECT's 10 s timeout (measured: 10.15 s → 1.14 s against a proxy that never answers). A synchronous render whose payload already carries both `rate_limits.five_hour` and `seven_day` does not fetch at all (`getUsage({ cacheOnly })`, served like lock contention): the fetch would only add the per-model weekly and `extra:` buckets, and it cost the whole budget on a slow proxy (1167 → 140 ms against a hung mock). A payload missing either window — a fresh session's first frame has none — still fetches, budgeted. Background refreshes are unbudgeted and keep the usage cache fresh. **The render lock (`render.lock/`, a `mkdir` lock) records its owner's PID** in `render.lock/pid`, and is taken over only when it is older than `HUD_LOCK_STALE_SECONDS` (10) *and* that PID is dead, or older than 120 s regardless (a hung render, a recycled PID). Age alone let a second render start beside an unbudgeted one still waiting on a silent proxy (~10 s), and the older one then landed last, over the newer line. The background subshell records its own PID (`sh -c 'echo "$PPID"'`), since its `$$` is the parent that exits at once; a lock is released only by the owner it names; and a takeover is serialized through a sibling `render.lock.reap/` dir with the staleness re-checked under it — without that, wrappers that all judged one lock stale each removed it and rendered side by side (2–4 renders per trial of 10 wrappers). **A payload that arrives while the lock is held is not dropped:** the frame that loses the lock touches `render.dirty` and then retries once, and the holder checks the flag *after* releasing, so one of the two always sees the other; the background refresh re-renders for it, up to 3 renders per refresh. Before, the last payload of a burst was never rendered, and an idle session showed a frame two payloads old. Orphaned `statusline.*.tmp` / `stdin.*.tmp` — and Node atomic-write temps (`.<name>.tmp.<uuid>`), including the usage cache's at the cache root — older than about two minutes (`-mmin +1`; GNU and busybox `find` truncate the age) are deleted whatever their size, by one `find` from the background refresh (with the other-session lock sweep and the daily prune; a synchronous render skips all three, since Claude Code is waiting on it) — not a per-file loop on the hot path: that cost ~6 forks a file, and forks are what is scarce when orphans pile up (a fork storm on the Windows box made one sweep of ~35 take 2m15s for the whole wrapper). A non-empty `statusline.<PID>.err` is kept, as the only record of why that render died. The docs describe `COLUMNS`/`LINES` as set for the command, but a live 2.1.261 hook process had neither, so the `maxWidth` auto-detect in `index.js` (which truncates the line to the terminal width, or wraps it at separators only under `wrapMode: "wrap"`) does not trigger through the wrapper. All runtime files — the shell's per-session render cache + `mkdir`-based render lock, *and* the Node HUD's state — live in a **per-session subfolder** of `cache/` (gitignored): `cache/<session>/<name>.json` (e.g. `stdin.json`, `statusline.txt`, `render.lock`, `lead-tokens.json`). Keep it relocatable: the cache dir is derived from the script dir (shell) / module location (Node), honors `HUD_CACHE_DIR`, and is never hardcoded. **No sweep runs in a cache dir without a `.vantagehud-cache` marker.** The prune `rm -rf`s every first-level directory past the retention age, so `HUD_CACHE_DIR=~/.cache` (or `$HOME`, `/tmp`) used to delete the user's own folders; the wrapper now writes the marker only in a dir it created itself and in the install's own `cache/` (which adopts existing installs), never in a pre-existing `HUD_CACHE_DIR`. **An unwritable default cache** (a read-only or shared install) falls back to `${XDG_CACHE_HOME:-~/.cache}/vantagehud`, exported as `HUD_CACHE_DIR` so Node follows; with no usable dir at all the wrapper renders the payload synchronously with nothing cached instead of printing `[HUD] Starting...` forever. The wrapper sets `umask 077`, so its files (`stdin.json` is the whole payload) are private like Node's 0600 writes. `HUD_DEBUG=1` makes the wrapper name its branch on stderr (`[HUD sh] …`) and pass on a good render's stderr instead of discarding it.
- `find-node.sh` locates `node` for non-interactive shells (PATH → nvm (`$NVM_DIR`, `${XDG_CONFIG_HOME:-~/.config}/nvm`, `~/.nvm`) → fnm (`$FNM_DIR`, defaults) → mise / asdf → Volta / homebrew / system) and always `exit 0` so it never blocks Claude Code. Each tool's default location is probed even without its env var, which a GUI-launched Claude Code often lacks. `statusline.sh` runs it with `sh`, so it only has to exist — not be executable.
- `statusline.mjs` installs an `HTTPS_PROXY`/`https_proxy` CONNECT tunnel by monkey-patching `node:https` **before** dynamically importing the HUD, then `import()`s `src/hud/index.js`. Credentials in the proxy URL become `Proxy-Authorization`, an `https://` proxy is dialed over TLS, and a CONNECT not answered with 200 (407/403) fails the request instead of handshaking on the proxy's error page. A bare `host:port` value is read as `http://host:port` (as curl does), an IPv6 literal is unbracketed before dialing, a `socks*` proxy is ignored (direct, with a `HUD_DEBUG` note), and a host covered by `NO_PROXY`/`no_proxy` (`*`, host, domain suffix, optional `:port`; no CIDR) bypasses the tunnel. Verified against a local authenticating CONNECT proxy (`scratchpad`-style harness, not checked in). `https`/`http`/`tls` are `require()`d (via `createRequire`, without the `node:` prefix that `require` accepts only from 14.18) **only when a proxy is set**: on Node 22+ a static `import` of `node:http` builds its ESM namespace, whose getters load undici — ~25 ms on every render. The CJS object is the one the HUD's `https` is, so the patch still covers it. The launcher also checks `process.versions.node` against the 14.17 floor: below it, a `HUD_DEBUG` note, and a load failure prints `[HUD] Node >=14.17 required (found vX)` instead of a bare `SyntaxError` — so this one file must stay free of `?.`/`??` and `node:` specifiers (verified on real 12.22.12 and 14.0.0 binaries).
- `src/hud/index.js:main()` builds a single `context` object from stdin + transcript (tail read plus the incremental tally memo) + usage API, then calls `render(context, config)`.

## Configuration

- User config lives in the HUD's **own `config.json`** at the install root (next to `cache/`), resolved by `getHudConfigFile()` in **`src/lib/install-paths.js`** (default `<install>/config.json`; `HUD_CONFIG` env overrides with an absolute path). It is **gitignored** (`/config.json`); the committed **`config.json.example`** is the canonical reference and mirrors `DEFAULT_HUD_CONFIG` — except `labels`, which it leaves `{}`: a copied full English set would override a `zh-CN` locale's labels. The file is **optional** — absent/unreadable ⇒ code defaults. Its top-level object **IS** the config (no wrapper key). `src/hud/state.js#readHudConfig()` reads it with `parseJsonText` (`src/lib/json-text.js`: `JSON.parse` minus a leading UTF-8 BOM, which Windows PowerShell writes), and a file that exists but does not parse yields the defaults flagged `configError`, which `render.js` shows as a leading `[cfg err]` (stderr never reaches the user on a good render). Under `HUD_DEBUG`, `mergeWithDefaults` names every key it does not read (top level, `elements`, `thresholds`, `contextLimitWarning`, `labels`), and it coerces `elements.maxOutputLines` to a positive integer; `src/hud/themes.js#readConfiguredTheme()` separately reads just `theme` from the same file at import. Precedence: `config.json` > defaults (theme also honors `HUD_THEME` env first).
- **Why its own file, not Claude Code's `settings.json`:** the HUD historically read a lowercase `statusline` block from `settings.json`, but that is **distinct** from the `statusLine` (capital-L) command-hook key (README). Claude Code's settings schema is a non-strict Zod object that **silently strips unknown keys** — so any non-schema config there (a lowercase `statusline` block, or anything nested inside `statusLine`) survives the HUD's own parse but gets wiped whenever Claude Code's settings tooling rewrites the file. `config.json` sidesteps that entirely. (The `statusLine` hook schema accepts only `type`, `command`, `padding`, `refreshInterval`, `hideVimModeIndicator`.)
- Defaults, labels (en + zh-CN), and the canonical element order (`DEFAULT_ELEMENT_ORDER`) all live in **`src/hud/types.js`**. Change defaults there — and keep `config.json.example` in sync.

## Adding or changing a statusline element

An element is a pure function `export function renderXxx(args) → string | null` (return `null` to render nothing; the string is a fragment with **no separators and no newlines** — `render.js` joins fragments with `" | "`, and its `put()` replaces any C0/C1 control other than ESC in a fragment with `?`, so a newline in a directory or repo name cannot split the line). The HUD renders a **single line**, so every element is an inline fragment.

To add one, touch these files (in order):
1. `src/hud/elements/<name>.js` — the render function. Use color helpers from `src/hud/colors.js` (`paint`, `paintLabel`, `paintFaint`, `PALETTE.*`), never raw escape codes.
2. `src/hud/render.js` — import it, guard on `enabledElements.<name>`, and store the result via `put("<name>", () => renderXxx(...))` (it catches, scrubs control characters, and skips `null`).
3. `src/hud/types.js` — add the enable flag to `DEFAULT_HUD_CONFIG.elements` and place `"<name>"` in `DEFAULT_ELEMENT_ORDER.main`.
4. `src/hud/index.js` — only if the element needs new data: extract it and add a field to the `context` object.

## Adding or changing a theme

- Palettes (the color **data**) live in **`src/hud/themes.js`** as the `THEMES` registry; **`src/hud/colors.js`** is the rendering **engine** (color-depth detection, `fg`/`paint`, gradient math) and exports the active palette as **`PALETTE`**. To add a bundled theme, add one entry to `THEMES` with all 10 tokens as **`#rrggbb` strings** (the file header documents each token's role) — **no other file changes**. Every element already routes through `PALETTE`/the `paint*` helpers.
- **Hex is the authoring format, `[r,g,b]` the runtime one.** `THEMES` entries and `config.json` palettes are both `#rrggbb` — deliberately identical, so a bundled and a user palette are the same shape, and a hex comment can't drift from an array. `resolvePalette` converts to the `[r,g,b]` triples `fg()` takes exactly once, at the end; `PALETTE` and every element are unchanged by this. Only `#` plus exactly 6 hex digits parses — no `#rgb`, no names, no arrays.
- Active theme is resolved **at import** in `themes.js#resolveThemeName`: `HUD_THEME` env > `config.json` `theme` > `DEFAULT_THEME` (`aurora`). It must be import-time, not render-time, because elements freeze `fg(PALETTE.x)` into module-level constants before `main()` reads the runtime config. That is also why `themes.js` keeps its own minimal parse of `config.json` (routing through `state.js#readHudConfig` would risk an import cycle; it shares only the import-free `parseJsonText`) — **one** parse now yields both `theme` and `themes`. `HUD_THEME=<name>` is the quick way to A/B a render, and it searches the *merged* registry, so it selects user themes too.
- **User themes (`config.json` `themes`) are colors only** — a partial or complete palette plus a reserved `base`. Deliberately no glyphs, no separator, no tier bounds: `sep`/`░` and ` | ` stay hardcoded (and `safeMode` rewrites the bar glyphs in `sanitize.js`), and the 70/85 cut points stay in `TIER_BOUNDS`/`thresholds` so a color can never disagree with the `COMPRESS?`/`CRITICAL` text beside it.
- Three resolution rules carry the weight, all in `resolveHexPalette`:
  - **Unset tokens come from `base`**, recursively. `base` defaults to the theme's *own* name when it shadows a bundled palette and to `DEFAULT_THEME` otherwise — defaulting it unconditionally to `DEFAULT_THEME` silently broke retinting for every bundled theme except aurora (`themes.ember = { label }` rendered *aurora* with one changed token, and nothing warned, because every name involved was valid). This is what makes a 1-token theme safe: a missing token would otherwise reach `fg(undefined)` and throw — and since most elements freeze `fg(PALETTE.x)` at module level, that throw happens at **import**, where it fails the whole renderer (`[HUD] load failed`), not one fragment. `render.js`'s per-element catch (`put`) only covers throws at render time. So the merge is the real guard, not the debug warning.
  - **A name already being resolved falls back to the *bundled* palette of that name.** One rule, two cases: `themes.aurora` whose `base` defaults to itself (a retint — the intended way to recolor a bundled theme in place), and a genuine `a → b → a` cycle. `MAX_BASE_DEPTH` backstops it.
  - **A malformed value keeps the inherited color** and warns under `HUD_DEBUG`; it never invalidates the whole theme. Same for unknown token keys.
- **Registry lookups are own-property only, and the registry has a null prototype.** Both matter, and both were bugs first: with plain `obj[k]`/`in`, a theme or `base` named `constructor` read as an existing palette and suppressed the unknown-name warning; and because `JSON.parse` makes `__proto__` a real own key, `themes[name] = value` on a `{}` registry invoked the inherited setter and re-pointed the registry's prototype, changing lookups for every *other* name. Use `has()` and `Object.create(null)`, never bare `in`.
- **Keys inside a theme are matched case-insensitively** through `CANONICAL_KEY`, like theme names — including `base`, which is why `readBase()` scans the keys instead of reading `user[BASE_KEY]`. A literal read accepted `"base"` but let `"Base"` fall through to the token loop, so the theme silently inherited the wrong palette while the only warning named a "token" that isn't one.
- **`preview-themes.mjs` (repo root) renders every theme — bundled *and* user-defined — in one process**, which is only possible because `resolvePalette(name)` is exported: `PALETTE` is frozen at import, so a process has exactly one *active* theme. It paints through the real `fg()`, so a preview cannot drift from a render; the sample *values* are hard-coded, so it is representative, not live. `--depth=0|1|2` re-execs itself with a doctored `TERM`/`COLORTERM` rather than second-guessing the detection in `colors.js`. Theme one-liner descriptions live in that script, not in `THEMES` — an 11th key would trip the parity check and `THEME_TOKENS`.
- Built-in themes: `aurora` (cool slate, the original — current default), `ember` (warm gruvbox), `nebula` (vivid Catppuccin-Mocha mauve), `graphite` (near-monochrome), `daylight` (the only one built for a **light** terminal background). New palettes were checked two ways before landing: WCAG contrast against the theme's intended background (`sep` is exempt — it is a hairline and a gauge track), and whether `rgbTo256`/`rgbTo16` keep tokens distinct after degradation. Counting every token pair whose source hex differs: at **256 colors** only `aurora` collides at all (`label`/`track`, both index 153); the other four are clean. At **16 colors** every theme collides, the originals worst of all — `aurora` 7 pairs, `ember` 8, against `nebula` 1 (`text`/`faint`) and `daylight` 2. `graphite` has 21, i.e. everything but the ramp goes white: accepted rather than fixed, because saturating those tints enough to survive `rgbTo16`'s `max - min < 40` neutral test would defeat the theme, and the `+`/`!`/`?`/`✗` glyphs still differ. Note `rgbTo16` also sends any near-neutral color with `max <= 120` to **black**, which on a dark terminal is invisible — that, not distinctness, is why graphite's `faint` is `#7d7d7d` and not darker. `DEFAULT_THEME` lives in `themes.js`; `THEME_TOKENS` derives the canonical 10 names from it, so the token list can't drift. The documented config defaults (`theme`, `themes`) live in `DEFAULT_HUD_CONFIG` (`src/hud/types.js`) and are **doc-only** — `mergeWithDefaults` drops both. Keep `config.json.example`'s `themes.custom` entry spelling out all 10 tokens.

## Conventions & gotchas

- **Rendering must never throw to the user.** Every layer swallows errors — `render.js` runs each element through `put()`, so one throwing element (logged under `HUD_DEBUG`) costs only its own fragment; an uncaught one becomes the `[HUD] HUD error - check stderr` line (stack in `statusline.err`), and the shell keeps the last good line only when the renderer printed nothing at all. Match this: wrap risky work in try/catch, fall back to `null`/empty, and gate noisy logs behind `HUD_DEBUG`.
- **State writes go through `atomicWriteJsonSync` (`src/lib/atomic-write.js`).** Never `fs.writeFileSync` a state/cache file directly — atomicity (temp + `fsync` + rename + dir `fsync`) is required because concurrent sessions race.
- **Cross-process coordination uses `src/lib/file-lock.js`** (`withFileLock`, `lockPathFor`). One attempt, no waiting: a held lock means the caller serves its cache. Lock files sit next to the data file and carry a PID, a start timestamp and a nonce; a lock is stale when older than the threshold **and** its PID is dead — or, whatever the PID says, older than 4× the threshold (a reused PID, or another user's, which reads as alive through `EPERM`, otherwise pinned it for days) or dated more than the threshold in the future (a clock stepped back). **Reaping is serialized through `<lock>.reap`** (exclusive-create, staleness re-checked under it, an orphan older than 5 s cleared): unlinking a stale lock without it let a late reaper delete the fresh lock an earlier one had just taken — reproduced with up to 7 of 8 processes holding one lock at once. Release unlinks only a file still carrying the holder's nonce.
- **State is centralized, never written into the user's project.** All runtime files live under one cache dir — by default the HUD install's own `cache/` (derived from the module's location in `getCacheDir`, so it follows a relocated install); `HUD_CACHE_DIR` overrides it and the shell wrapper honors the same var, so the two layers never diverge. Each session gets its **own subfolder** named by the (sanitized) session id, and the files inside drop the suffix: `cache/<session>/hud-stdin-cache.json`, `.../compact-requested.json`, `.../subagent-tokens.json`, `.../lead-tokens.json`, `.../svn-status.json` (plus the shell's `stdin.json`, `statusline.txt`, `render.lock`). There is no `hud-state.json` any more — the session start it persisted is part of the `lead-tokens.json` memo. The globally-unique session id naming the folder keeps unrelated sessions **and** projects from colliding, so there is no per-project subdirectory (and the stdin/stabilization cache can no longer be clobbered across sessions). Always resolve via `src/lib/worktree-paths.js` (`getSessionCacheDir`, `sessionCacheFile`; `atomicWriteFileSync` creates the folder); never hardcode. The session key is derived once in `index.js#resolveSessionKey` (`HUD_SESSION_KEY`, the key statusline.sh computed and exported so the two layers can never diverge, even on its checksum fallbacks → stdin `session_id` → session-id env vars → transcript UUID → `default`) and threaded into every cache read/write. Session folders idle longer than `HUD_CACHE_MAX_AGE_DAYS` (default 14) — and legacy flat cache files — are pruned at most once a day from the shell's background refresh — in effect after 15 idle days on GNU/busybox `find`, which truncates `-mtime` to whole days (BSD rounds up, so 14 there) — and only in a cache dir carrying the `.vantagehud-cache` marker.
- **Width math uses `stringWidth()` from `src/lib/string-width.js`, not `.length`** (ANSI is stripped first; CJK and every East_Asian_Width=W symbol in U+2000-2BFF count as 2; variation selectors and skin-tone modifiers as 0; a regional indicator as 1, so a flag is 2). Emoji width is still approximate: ZWJ sequences count every member, and a text-default symbol plus VS16 counts 1.
- **`safeMode` (default `true` on every platform; an explicit `false` disables it, Windows included) changes output:** it strips non-SGR ANSI and swaps Unicode bar glyphs for ASCII via `src/hud/sanitize.js`. Outside safe mode, `index.js` replaces spaces with non-breaking spaces (`\u00A0`) for alignment — keep both paths working.
- **Usage/rate-limit data (`src/hud/usage-api.js`)** reads OAuth creds from the macOS Keychain or `~/.claude/.credentials.json`, calls `api.anthropic.com/api/oauth/usage`, and caches with backoff in one file per account at the cache root, shared by all sessions: `.usage-cache-anthropic.json` for the default config dir, `.usage-cache-anthropic-<fnv1a>.json` when `CLAUDE_CONFIG_DIR` is set (`getAccountSuffix` — the credentials are found by that variable, so it is the account key). One shared file used to show one account's numbers in another account's session. It is intentionally suppressed when `ANTHROPIC_BASE_URL` points at a non-Anthropic gateway (an empty value counts as unset, as in Claude Code), and when `CLAUDE_CODE_USE_BEDROCK` / `_VERTEX` / `_FOUNDRY` is on (anything but empty, `0`, `false`, `no`, `off`) — a leftover subscription login would otherwise show limits the provider's traffic does not draw on. **Credentials are strictly read-only — the HUD never refreshes an expired token.** OAuth refresh tokens are single-use, so a refresh from a hook revokes the access token Claude Code itself holds and forces a re-login (anthropics/claude-code#42603, closed with "remove all token refresh logic from hooks"); the old refresh + write-back was exactly that. An expired token yields `error: 'auth'`: the cached per-model weekly and `extra:` buckets are served while under 15 min old, then `[API auth]`, until Claude Code rewrites the store on its own (the `auth` cache TTL is 15 s, so it is re-read promptly). A **401** — a token valid by its clock that the server rejects (revoked, or rotated by a `/login` elsewhere) — is `auth` too; the entry stores a sha256 fingerprint of the rejected token (never the token), so the 15 s re-read does not re-send that same token faster than the 2-min transient pace. A 403 stays `network`: the region block answers 403 as well. A 429's numeric `Retry-After` is honored (capped at 1 h), and no 429 backoff is ever shorter than the poll interval. When `getUsage` does not fetch — the usage lock is held by a peer, or cannot be taken at all (EACCES, ENOSPC, Windows EPERM) — it serves `serveWithoutFetch`: data under 15 min old, stale-marked, else only an error the cache itself recorded. A peer mid-fetch is not a failure; reporting it as `network` put an invented `[API err]` on the line, and a synchronous first frame cached it. Current Claude Code puts `five_hour`/`seven_day` in the payload's `rate_limits`, which take precedence in `mergeStdinRateLimits` and are live and unmarked throughout — that merge also drops the API's `stale` flag, because the `*`/`~` marker is per fragment and would otherwise paint the payload's fresh numbers; only when the payload carries no `rate_limits` at all (older Claude Code) are the API's numbers rendered with the marker. **A window whose reset time has passed is not rendered** (`hasReset` in `limits.js`): Claude Code drops such a window from the payload, and the merge used to fill it back from the API cache with the pre-reset percent, unmarked (`5h:92%` right after the reset). A window with no reset date is kept, since the API can send `resets_at: null`; a payload that merely lacks a window is not read as a reset, as windows may be independently absent. **Per-model weekly caps moved into the response's `limits[]`** (`kind: "weekly_scoped"`, `scope.model.display_name`); the flat `seven_day_opus`/`seven_day_sonnet` are null on current accounts (measured 2026-10). `parseUsageResponse` reads the flat fields first and `limits[]` as the fallback: `session`/`weekly_all` for an absent `5h`/`7d`, Sonnet/Opus into `sn:`/`op:`, any other model into `modelWeekly` (label = first letter + first consonant after it, so `fb` for Fable; letters only, since the name is server text), gated by `sonnetWeeklyVisibility` like `sn:`. A surface-scoped entry is skipped. When testing the endpoint by hand, set `HTTPS_PROXY` exactly as the live session has it: from this machine a **direct** egress gets `403 forbidden / Request not allowed` (region block), and only the tunnel reaches it — which is also why a local test proxy that connects upstream directly can never observe a 200.
- **`token:` folds in teammate/subagent tokens (`src/hud/subagents.js`).** Claude Code writes each subagent to its own transcript under `<lead-transcript>/subagents/` (sharing the parent `sessionId`), which the lead transcript `parseTranscript` reads never contains — so `sessionTotalTokens` would undercount every multi-agent run (often ~half). **There are two layouts, and the walk must stay recursive to catch both:** Agent-tool teammates land flat at `subagents/agent-*.jsonl`, but Workflow-tool ("ultracode") agents nest one level deeper at `subagents/workflows/wf_<id>/agent-*.jsonl`. A flat `readdir` sees only the `workflows` *directory*, which fails the `agent-` prefix test — so every workflow run scored 0 and hid the bulk of a session's tokens (measured: 667k of 872k on a real 30-agent run). Recursion is hand-rolled: `readdirSync`'s `recursive` option is Node 18.17+ and this project floors at 14.17. Descent is bounded by `MAX_WALK_DEPTH` and follows `isDirectory()` (false for symlinks, so cycles can't trap it). `index.js` adds `sumSubagentTokens(resolvedTranscriptPath, sessionKey).total` to the lead total from `tallyLead(...).totalTokens` (null stays null → element still hides). **The subagent figure is a lower bound on current Claude Code, not exact:** from 2.1.283 most subagent calls never get a settled row — the last row of the `message.id` group keeps `stop_reason: null` and the `message_start` placeholder (`output_tokens` 2–32), and the settled count is written nowhere (measured: 1,176 of 1,289 groups on 2.1.289, 32/35 on 2.1.286, 7/8 on 2.1.283, 24/337 on 2.1.261; 0 of 1,521 lead groups on any version). `tallyFile` counts closed groups like that in the memo's `unsettled` (only an explicit `null` counts), `sumSubagentTokens` also counts a file's open last group once the file has stopped growing (`lastSettled === false` on the stamp fast path), and either one makes `token:` render as `token:~…` (`sessionTokensApproximate`). No estimate is added on purpose: thinking text is redacted to a `signature`, chars/token on settled groups ran 1.07–2.25 by thinking mode, and one ratio landed within ±25% on only 9–40% of groups (aggregate −28%). Check whether settled rows come back on each new Claude Code version. Per-file tallies are memoized on disk (`subagent-tokens.json`, a `tallyFile` memo plus a size+mtime stamp, under each file's path *relative to* the subagents dir) because the one-process-per-render model kills in-memory caches; an untouched team costs one `stat()` per file. Fails to 0 on any read error, and a single vanished/rotated file keeps its last good sum rather than zeroing the team — **which works only because the fast path also requires `hit.consumed === file.size`**. `tallyFile` signals failure by returning a memo short of the file end; without that check one unreadable frame would be stamped as authoritative and, since a finished transcript never changes size or mtime again, freeze that teammate at 0 for the whole session (reproduced, then fixed). Every file found is summed and keeps its memo — one workflow can spawn 1000 agents. `MAX_TALLIES_PER_FRAME` (512) bounds only how many changed or unseen files are *parsed* in one frame: past it a changed file adds its last memo total, an unseen one adds 0, `token:` shows `~` until a later frame catches up, and `HUD_DEBUG` says how many were left. It replaced a cap that summed only the 512 *largest* files: a small file outgrowing a token-heavy one evicted it, so the total ran backwards (1,000,511 → 513 in a 513-file fixture) and its memo was pruned. **Both sides count through `src/hud/token-tally.js` (`tallyFile`), never by summing rows.** Two bugs forced this and both are fixed there, so do not reintroduce a naive row sum:
  - *One API call writes several rows.* Claude Code emits one row per assistant **content block** (`thinking`, `text`, each `tool_use`), all sharing one `message.id`/`requestId` and each carrying that call's usage. Summing rows counted a call 2–4×. `tallyFile` de-duplicates on `message.id`, **last row wins — and the reason matters**: the rows of a group are *not* identical (10,178 of 35,751 groups across 509 transcripts differ per row; early rows can hold a placeholder, e.g. `output_tokens` `3, 3, 6205`), but they are **monotonically non-decreasing** (0 decreasing steps), so last-wins and max-wins agree while first-wins would be badly wrong. (On current subagent files the last row can itself be the placeholder — the `unsettled` case above.) Measured across all 159 transcripts on the dev machine at the time: **median 2.46×, max 4.11×** inflation; on the ultracode session that prompted this, 2,825,110 → **2,484,323** (lead alone 379,393 → 161,157). Subagent files inflate far less (~1.05× on that session) than leads (the 2.46× corpus median above; that session's own lead was 2.35×), so a heavy multi-agent run *dilutes* the error rather than showing it.
  - *Tail-reading silently truncated the total.* The old lead path parsed only the last 4 MiB yet published the result as a complete session sum — measured on a 25.4 MB transcript as 739,480 against a true 1,910,334 — **39% of the truth** (14 leads exceeded 4 MiB at the time), and since the window is a fixed byte count, one large `tool_result` could evict usage rows and make the counter run **backwards**. `tallyFile` scans the whole file *incrementally* instead: transcripts are append-only, so each frame parses only the newly appended bytes and resumes a memoized running total (lead memo: `lead-tokens.json`). A full cold scan of that 25.4 MB file costs ~260 ms — far too slow per frame, which is why the memo is load-bearing, not an optimization. The unread range is read and decoded in 8 MiB slices (`SLICE_BYTES`, each cut after its last newline, widened only for a longer single line), not as one string: a range past V8's ~512 MiB string limit used to throw on every frame, and peak memory on a cold scan was about 3× the file.
  - Two verified on-disk properties make the incremental design safe: rows sharing a `message.id` are **contiguous** among usage rows (0 exceptions in 73,748 rows / 509 transcripts), so only the last group can straddle a chunk boundary (`lastId`/`lastIdTokens` correct it) — note this fails *silently* in both directions if ever violated, nothing asserts it; and a `message.id` is never shared between **files that get summed together** (0 between a lead and its own `subagents/`, 0 between sibling subagent files, over 56 sessions with teammates) — that, not the `isSidechain` argument, is why lead+subagent addition double-counts nothing. Ids *are* shared more widely — 30 appear in up to 5 files — but only across **forked** sessions, which are separate leads never added to their parent. An FNV-1a `fp` over the first 512 bytes plus an `isLineBoundary` check at the resume offset make it very unlikely that a memo no longer matching the bytes there is trusted — `isLineBoundary` misses only a shift that leaves a `\n` at exactly that offset (a different file in the same slot, or a rewrite that shifts content) and force a rescan; a shrink does too. Compaction is *not* such a case — it appends `compactMetadata` rows to the same growing file.
  - `parseTranscript` therefore computes nothing cumulative: it tail-reads 4 MiB for `lastRequestTokenUsage` only (feeds `ctx:`, wants exactly the last row), and `index.js` calls it only when the payload's context % is 0 — the one case that reads it. It scans that window backwards and stops at the last usage row, so it usually parses one line, not every line in 4 MiB (5.5 MB transcript: ~28 ms → ~2 ms). The **tool/agent/skill counts and the session start** ride the same tally memo (`tallyLead` → `toolCalls`/`agentCalls`/`skillCalls`/`firstTimestamp`), for the same reason: read from the tail they were truncated on any large transcript (measured on a 4.9 MB one: 442 of 494 tool calls, 2 of 3 agent calls) and ran backwards as the window slid. Counting per row is safe because each assistant row carries exactly one content block (0 rows with several, 0 repeated `tool_use` ids, across 50 transcripts / 16,330 rows). A memo lacking the counters (written before they existed) is not resumable and rescans once — the lead's, and in `subagents.js` any teammate file that has *changed* since (an unchanged one keeps its old memo through the stamp fast path, which is fine: only the lead's counts are rendered). A memo lacking `unsettled`/`lastSettled` rescans once too, and that one *does* bypass the stamp fast path, since every teammate's flag is rendered; `tallyLead` persists on any field change (`sameMemo`), which is what makes that migration cost one frame instead of a rescan every frame.
- **`gitRepo`/`gitBranch`/`gitStatus` are VCS slots, not git-only elements.** A Subversion checkout gets the same three fragments (`repo:proj | branch:2.1@12345 | ✗2 +2 !3 ?1`) under the same three config keys — there are no `svn*` flags to enable. **`render.js` picks the VCS once** (`useSvn`) rather than per slot: a per-slot `renderGitX(...) ?? renderSvnX(...)` lets the slots disagree, because `renderGitRepo` returns null with no `origin` remote and `renderGitStatus` returns null for a *clean* tree — so a git clone inside an SVN working copy would show the SVN project beside a git branch, and its clean tree would fall through to `svn status`, which reports that directory as unversioned. Git wins ties. The repo name and the worktree suffix come from the payload's `workspace.repo.name` / `workspace.git_worktree` when present (`index.js` → `context.repoName` / `context.worktreeHint`; the hint is trusted only alongside `repo`, since `git_worktree` is the older field — 2.1.97 against ≤2.1.233 for `repo` in the cached payloads), which spares `git remote get-url` and the two `rev-parse` calls: a frame in a git repo spawns 3 git processes instead of 6, `branch --show-current` and `status` being the survivors. Cost otherwise is one `git rev-parse` for the decision plus, on the SVN side, a **filesystem** walk for `.svn` (`findSvnWorkingCopyRoot`, `src/lib/worktree-paths.js`, which `realpathSync`es first so a symlinked cwd still finds the root, and stops at the first `.svn` holding `wc.db` — climbing on past it made a cwd inside an `svn:externals` directory or a nested checkout report the *outer* working copy; only pre-1.7 layouts, with no `wc.db`, climb to the topmost contiguous `.svn`): a git checkout never spawns `svn`, and an SVN checkout never spawns the three git element commands.
  - `src/hud/elements/svn.js` shells out only after that gate, and only to `svn info|status --xml --non-interactive`: `--xml` avoids the locale-dependent text output, `--non-interactive` makes a credentials prompt impossible, and the **absence of `-u`** keeps both commands local — which is also why SVN has no ahead/behind (`⇡`/`⇣`) counterpart.
  - **Both status columns count.** `wc-status` carries `item` *and* `props`, and reading only `item` scored a property conflict (`item="normal" props="conflicted"`) and a property-only edit as clean — the latter being the normal state of every merge root, since `svn merge` writes `svn:mergeinfo` there. Mapping: `added`/`deleted`/`replaced` → staged (SVN has no index; "staged" means scheduled for commit), `modified`/`merged`/`missing`/`incomplete` → modified, `unversioned` → untracked, `conflicted`/`obstructed`/`props="conflicted"`/any `tree-conflicted="true"` → conflicted, and `props="modified"` → modified but checked last so a path is never counted twice. Note `svn status` descends into externals (one extra `<target>` each), so their changes are counted individually — git would show a dirty submodule as one entry.
  - **`svn status` walks the whole working copy, so its counts are memoized to `cache/<session>/svn-status.json`**, not to the module-level Maps — one process per render kills those, exactly as for `subagents.js`. **The memo has two independent invalidation triggers, ORed, and neither is redundant:** a 30 s TTL, and a change stamp (`mtimeMs:size`) over the working copy's `.svn/wc.db`. On the clock alone an `svn delete` stayed invisible for up to 30 s — reproduced, and the reason the element looked broken. Every *metadata* operation commits a SQLite transaction to `wc.db`, so its mtime is a ~µs proxy for "the schedule changed": **measured** to move for `svn delete`, `add`, `revert` and `propset`, and — load-bearing — **not** to move for `svn status` itself, so a read cannot invalidate its own memo. It equally **measurably does not** move for a versioned-file edit, a plain `rm` (`missing`), or a new unversioned file: those are pure working-file changes touching no metadata, and only the TTL catches them. Same for externals — each carries its own `.svn/wc.db`, and the root's stamp says nothing about theirs. The stamp is read *after* the walk, so a future `svn` that wrote wc.db while reporting status could not put every frame into a rescan loop. No `wc.db` (pre-1.7) ⇒ stamp `null` on both sides ⇒ TTL alone, i.e. the old behaviour. **A failed rescan backs off** (`failedAt` in the memo, `STATUS_FAILURE_BACKOFF_MS` = 5 min) and **a synchronous render never walks** (`HUD_SYNC_RENDER`: memo at any age, else no fragment). Without both, a working copy whose walk outlasts `STATUS_TIMEOUT_MS` (3 s) never gets a memo written, so every frame pays the full timeout and fails again: a 28 s `svn status` on a Windows checkout put ~3.2 s into every render (bisected there), and a 5 s shim reproduces it here — 3.1 s per frame before, ~150 ms after. Measured on a 96k-file checkout with 8 externals: `svn status` ~510 ms, a cold HUD frame ~693 ms against ~175 ms on a memo hit. Without the memo every frame re-walked the tree, and on a large checkout that both stalls the synchronous first render and blows the timeout, leaving the fragment empty forever. A rescan that fails or times out serves the last good counts rather than blanking. `svn info` is a single-file read and stays per-frame, which keeps the revision fresh across `svn update`. `execFileSync` also needs an explicit `maxBuffer` here: it **throws** ENOBUFS past 1 MiB, and `svn status --xml` spends ~90 bytes per unversioned path, so an unignored build directory would silently delete the element.
  - `resolveToWorktreeRoot` mirrors the same order (git root → SVN working-copy root → the directory as given). It used to substitute `process.cwd()` for any non-git directory; since `statusline.sh` never `cd`s, that usually *was* the session's cwd, but it diverges whenever the hook is invoked from elsewhere (the smoke test is such a case) — and returning the SVN working-copy root, plus dropping an unconditional stderr line, are wins regardless.
- WSL detection and process-liveness go through `src/lib/platform.js`; plain OS branches (`process.platform === 'win32' | 'darwin'`) still appear inline where simpler.
